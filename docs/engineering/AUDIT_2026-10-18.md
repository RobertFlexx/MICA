# MICA 2.0 follow-up engineering audit, 2026-10-18

## Scope and baseline

The supplied repository contained the complete assembler, constrained ELF
reader/writer, linker, emulator, transactional RTL, 2.0 ISA tables, diagrams,
firmware and a pre-existing hardware evidence archive. Initial clean GCC 14.2
Release build succeeded, with **9 of 9 CTest suites passing**. This did not
prove the advertised 2.0 ELF integration: those suites primarily used raw 2.0
images and legacy ELF objects.

A fresh executable confirmation showed that `mica-as --mica2 -c` wrote
`e_flags=0x10000` (MICA-32, MICA2 bit), while `mica-ld` rejected the object
with `unknown MICA ELF flags`. The reader still only admitted `0xff01`.
The emulator also failed to include the MICA2 bit in its executable feature
check. This was a real compatibility defect, despite the green baseline suite.

## Implemented corrections

| Area | Change | Purpose |
| --- | --- | --- |
| ELF headers | Explicit shared feature mask, validated on read **and** write | Admit the reserved 2.0 bit without admitting arbitrary flag bits |
| Linker | Reject mixing 1.0/2.0 objects and mixing XLENs | Preserve changes to legacy instruction semantics |
| Emulator | Require the ELF revision to match the selected execution mode, check extensions | Prevent running old objects with new semantics or missing hardware options |
| Inspector | Show ISA revision and extension requirements | Diagnose unsupported objects before executing them |
| Relocations | Add `ADRPC16` for existing WIDE/ADRPC opcode, with template validation | Link symbols from other object files without a new instruction encoding |
| Displacements | Checked unsigned distance and explicit PC-relative bases | Avoid signed-wrapped subtraction at 64-bit address boundaries |
| Assembler | Reject empty trailing operands and symbolic/oversized relocation addends | Prevent malformed source and relocation corruption |
| SDK examples | Add cross-object MICA-32/64 data access routines | Exercise full assembler to linker to emulator integration |
| Source formatting | Stage formatting before writing; add selective paths and semantic-sensitive exclusions | Avoid half-formatted source trees and altering shell/YAML data |
| Diagram | Update emulator/ELF flow DOT, SVG, PNG and PDF plus hash manifest | Represent the actual loader feature gate |

The new relocation calculates `(S+A-P)/2` where `P` is the address of the
`adrpc` itself. Ordinary branch relocations continue to use their next-PC
base. Signed 16-bit halfword displacement limits, the long-instruction template
and 2-byte target alignment are checked before modifying the image.

No architectural instruction opcode was added or changed. No RTL datapath,
register count, timing path or FPGA constraint was altered as part of this
follow-up, so the changes do not establish higher IPC, smaller RTL area, or
lower electrical power.

## Reproducible software checks

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 6
ctest --test-dir build --output-on-failure

cmake -S . -B build-san -G Ninja -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer' \
  -DCMAKE_EXE_LINKER_FLAGS='-fsanitize=address,undefined'
cmake --build build-san --parallel 4
ctest --test-dir build-san --output-on-failure
```

`tests/elf_revision.py` covers MICA-32 and MICA-64 multifile ELF programs,
forward/backward PC-relative relocations, actual published firmware examples,
ELF version flags, legacy rejection, disabled extensions, malformed flags,
range/alignment/template failures and assembler diagnostics.
`tests/format_safety.py` verifies that formatter errors leave source unchanged.
Existing frozen binary compatibility tests must keep passing.

The published cross-object `adrpc` examples execute five instructions and
produce `x1=0x2a` for both widths. Linked images at origin `0x1000` are
20 bytes (MICA-32) and 24 bytes (MICA-64), including linker padding and data.
These are software instruction counts and image sizes, not hardware cycle
counts or benchmark evidence against RISC-V or ARM.

## Hardware validation boundaries

The existing archived RTL/synthesis reports are part of the input repository,
not freshly established measurements for this follow-up. Here Graphviz and
MICA2 drawing-source checks are available. Verilator, Icarus Verilog, Yosys,
GHDL, FPGA vendor implementation and physical board access are absent. Do not
interpret pre-existing mapped cells or diagram preview hashes as current
place-and-route, timing closure, electrical power or physical chip tests.

The highest-priority unfinished engineering tracks remain a real C/LLVM
backend, improved stack/register allocation, optional signed post-increment
loads, a pipelined core, enhanced interrupt control, complete DSP/atomic RTL
coverage, cross-core memory semantics, physical FPGA validation and matched
workload/area/energy benchmarks. The MICA-2C MCU area budget must remain
separate from any server-class proposals.

This is an audited software-and-toolchain increment to MICA 2.0, not a claim
that the full processor architecture or its hardware ecosystem is complete.
